## Executive summary

M0 did what it set out to do. Streaks, puzzle numbers, midnight solves and win rate now work correctly. A missing or unreachable puzzle gives an error with Retry, or a clearly labelled fallback, instead of nothing or an unsolvable board. Every puzzle and every change is now checked automatically, and the game reports the events needed to measure activation, completion, drop-off and retention. The evaluation also caught a regression introduced by M0 itself: the daily puzzle Action failed today, because the new puzzle check needs packages the Action never installed. It is fixed in #43, which must merge before tomorrow's run. Next highest-leverage step: merge #43, then start M1's first-impression work, keeping M3's mobile layout close behind given the device split.

## What M0 taught us

- **Make CI match every place code runs.** CI installed packages; the daily Action didn't. #43 closes that gap. Any future workflow that runs repo code should install dependencies and get a CI step running the same command.
- **The fallback paid off on day one.** If #43 hadn't been caught, players would have reached 10 Nov with no puzzle, and TRI-010 would have served 9 Nov's with a notice instead of an unsolvable board.
- **The data is too thin to steer by yet.** Decisions in M1 still rest on the review and on watching players (R-05). Re-check the metrics at the M1 review.

## Recommended next steps

1. **Merge #43 today, then run the daily Action manually** to publish 10 Nov. Confirm the supply and live-site checks pass in that run, which completes TRI-012 and TRI-013.
2. **Finish M0's follow-ups:** build the Umami funnel (TRI-020), confirm the Edmonton location, and compare a week of Umami and Vercel counts (TRI-081).
3. **Start M1** with the first-impression items (TRI-026, 027, 029, 031). Given that about 61% of visitors are on mobile (Vercel), consider pulling TRI-058 (board and pad fit small phones) forward from M3, as R-03 suggests.
